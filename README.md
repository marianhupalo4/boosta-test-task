# ADHD test funnel

Повний сценарій **Quiz → Account creation → Report → Sign in**:

- квіз доступний без акаунта;
- після проходження користувач створює акаунт (email + пароль) і бачить персональний репорт;
- існуючий користувач входить окремо через Sign in;
- тест можна пройти повторно, після чого актуальний репорт оновлюється.

| Частина | Стек |
|---|---|
| `apps/web` | Next.js 16 (App Router), React 19, Tailwind CSS 4 |
| `apps/api` | NestJS 11, Prisma 7, PostgreSQL |
| `packages/shared` | Спільні типи та zod-схеми, тобто контракт між web і api |

**Робоча версія:** https://boosta-test-task.vercel.app (API: https://boosta-test-task.onrender.com/api/health). Безкоштовний план Render засинає після простою, тому перше відкриття може тривати до 50 секунд.

## Запуск локально

Потрібні Node.js 22+, pnpm 10 і Docker.

```bash
pnpm install
cp apps/api/.env.example apps/api/.env
cp apps/web/.env.example apps/web/.env.local

pnpm db:up       # PostgreSQL у Docker на порту 5434
pnpm db:setup    # міграції + сид квізу
pnpm dev         # web: http://localhost:3000, api: http://localhost:4000
```

### Тести

```bash
pnpm test        # unit + e2e тести API (окрема БД adhd_test у тому ж контейнері)
pnpm test:ui     # Playwright: повний флоу в браузері, desktop і mobile (потрібен запущений pnpm dev)
```

Для Playwright один раз потрібно встановити браузер: `pnpm --filter web exec playwright install chromium`.

Якщо том Postgres було створено до появи `docker/init-test-db.sql`, тестову БД треба створити вручну:

```bash
docker compose exec db psql -U adhd -c 'CREATE DATABASE adhd_test'
```

## Як це працює

```
Browser ──► Next.js (web) ── rewrite /api/* ──► NestJS (api) ──► PostgreSQL
```

Браузер звертається лише до origin веб-застосунку. Next.js проксує `/api/*` на API, тому сесійні httpOnly-cookie є first-party, і CORS не потрібен. При цьому застосунки лишаються окремими: їх можна збирати, деплоїти й масштабувати незалежно. Серверні компоненти Next.js звертаються до API напряму і передають cookie відвідувача.

### Флоу

1. `GET /api/quizzes/adhd/active` повертає активну версію квізу без ваг для підрахунку. Перше питання (`gender`, layout `intro`) — це стартовий екран Male / Female з дизайну.
2. Відповіді накопичуються на клієнті (з localStorage, щоб пережити перезавантаження) і відправляються одним запитом `POST /api/attempts`.
3. Сервер перевіряє відповіді на відповідність саме тій версії квізу, рахує результат, будує репорт і зберігає все в одній транзакції.
4. Анонімне проходження отримує випадковий claim-токен у httpOnly cookie (у БД зберігається лише його sha256). На `sign-up` або `sign-in` проходження прив'язується до користувача.
5. `GET /api/reports/me` повертає репорт останнього проходження користувача.

### Модель даних

| Таблиця | Що зберігає |
|---|---|
| `quiz_versions` | Незмінні версії квізу: `definition` (питання, JSONB), `scoring` (стратегія + параметри), `report_template`. Частковий unique-індекс гарантує, що активна лише одна версія на квіз. |
| `attempts` | Проходження, прив'язане до своєї версії квізу; `user_id` порожній, доки проходження анонімне. |
| `attempt_answers` | Одна відповідь — один рядок, ключ `(attempt_id, question_key)`, значення в JSONB. |
| `attempt_results` | Бал, outcome і стратегія, якою його пораховано. |
| `reports` | Snapshot секцій репорту з ключем і версією шаблону. |
| `users` | Email та argon2-хеш пароля. |

## Ключові архітектурні рішення

- **Версіонування квізу.** Опублікована версія ніколи не змінюється. Зміна питань чи підрахунку означає новий файл у `apps/api/src/quiz/definitions` і новий запис у `QUIZ_VERSIONS`. Сид ідемпотентний: створює нові версії, активує останню, а спроба змінити вже опубліковану версію завершується помилкою.
- **Стабільні ключі питань і варіантів** (`misplacing_items`, `strongly_agree`) замість індексів чи текстів. Відповіді зберігаються за цими ключами, тому їх можна порівнювати між версіями. Якщо питання за змістом інше, воно отримує новий ключ.
- **Підрахунок результату як стратегія.** Версія квізу посилається на стратегію за ключем (`likert-sum-v1`) і зберігає її параметри: ваги, поріг, перелік питань. Нова логіка — це нова стратегія; старі лишаються зареєстрованими, тож старі проходження інтерпретуються так само, як раніше.
- **Репорт із секцій.** Шаблон (`adhd-v1`) — це впорядкований список секцій. Кожна секція має `type`, `version`, необов'язковий `isApplicable(ctx)` і `build(ctx)`. Контекст містить відповіді за ключами, результат і `loadHistory()` з попередніми проходженнями користувача. Контент (тексти для High/Low × Male/Female) лежить окремо від логіки.
- **Snapshot репорту.** Репорт будується в момент проходження й зберігається разом із ключем і версією шаблону, тому зміна логіки чи текстів не переписує вже виданих звітів.
- **Фронтенд, керований даними.** Квіз рендериться з `definition` (layout `intro` / `default`), репорт — через мапу `section.type → компонент`. Невідомі типи секцій пропускаються, тож API може додати нову секцію раніше, ніж фронт навчиться її показувати.
- **Мінімальна авторизація.** JWT у httpOnly-cookie, хешування argon2 і rate limit на `/auth/*`. Email і пароль валідуються спільними zod-схемами і на клієнті, і на сервері.

## Як рішення враховує зміни тесту й репорту

| Зміна | Що робимо | Що відбувається зі старими даними |
|---|---|---|
| Змінились питання | Нова версія квізу (`adhd-v2.ts`) з власним `definition` | Старі проходження посилаються на v1, яка лишається в БД (archived) |
| Змінилась логіка балу | Нова стратегія або інші параметри в новій версії | Старі результати збережені разом із назвою стратегії |
| Змінились тексти чи логіка репорту | Новий шаблон або нова `version` шаблону | Видані репорти — це snapshot, вони не змінюються |
| Секція залежить від конкретної відповіді | `isApplicable: (ctx) => ctx.answers.get('key')…` | Нічого: секція читає відповідь за стабільним ключем, а не за позицією |
| Секція порівнює з попередніми проходженнями | `await ctx.loadHistory()` повертає попередні проходження з відповідями за ключами | Історія всіх проходжень зберігається |

Гендерні варіанти репорту працюють через той самий механізм: гендер — звичайне питання квізу, а секції читають відповідь на нього.

Ці гарантії перевіряє e2e-тест на справжній БД (`apps/api/test/flow.e2e-spec.ts`). Тест публікує нову версію квізу (одне питання змінене, одне нове) і перевіряє три речі:
- репорт попереднього проходження не змінився;
- нові відповіді на стару версію відхиляються;
- нова секція будується з відповідей і результату попереднього проходження.

## Логіка результату

Стратегія `likert-sum-v1`:

- кожна відповідь має вагу від 0 до 4 (Strongly agree = 4, … Strongly Disagree = 0);
- сума ваг 5 питань нормалізується до шкали 0–100, як на гейджі в дизайні;
- `score >= 60` → **High ADHD Traits**, інакше → **Low ADHD Traits**. Це узгоджено з макетом: 52 — Low, 74 — High.

Принцип такий самий, як у скринінговій шкалі ASRS v1.1: частота симптомів → бал → поріг. Самі питання взято з дизайну. Поріг і ваги — параметри версії квізу, а не код.

## Trade-offs

- **Відповіді надсилаються одним запитом**, а не по кроках. Простіше й атомарно, у БД немає незавершених проходжень. Натомість немає аналітики відпадання по кроках і продовження на іншому пристрої.
- **JWT без refresh-токенів і серверних сесій.** Цього достатньо для мінімальної авторизації з ТЗ, але токен неможливо відкликати до закінчення терміну дії (7 днів). Sign out лише видаляє cookie.
- **Snapshot репорту дублює дані**, зате історичні звіти стабільні. Перебудову репорту можна додати як окрему явну дію.
- **Snapshot будується в момент проходження.** Для анонімного проходження історія ще недоступна: майбутні секції з порівнянням проходжень доведеться будувати під час прив'язки до акаунта або під час читання.
- **`definition` квізу зберігається в JSONB**, а не в нормалізованих таблицях питань. Так легко версіонувати цілком, а для запитів за конкретними питаннями є нормалізована `attempt_answers`.
- **Версії квізу описані в коді й потрапляють у БД через сид**, а не через адмінку. Це дає code review для кожної зміни квізу.
- **Після прив'язки проходження «актуальний» репорт — останній за часом проходження.** Якщо користувач увійде в акаунт після анонімного тесту, новий результат стане актуальним, як і вимагає ТЗ.
- **`trust proxy` увімкнено,** бо всі запити приходять через проксі веб-застосунку, і інакше rate limit спрацьовував би на всіх користувачів разом. Ціна: клієнт, який звертається до API напряму, може підробити `X-Forwarded-For`. У продакшені це закривається приватною мережею між web і api.

## Що не зроблено і чому

- **Підтвердження email, відновлення пароля, OAuth** — поза межами ТЗ.
- **Адмінка для редагування квізів і A/B-тести версій** — для тестового завдання вистачає версій у коді.
- **Збереження прогресу квізу на сервері** — див. trade-offs.
- **Pixel-perfect верстка та i18n** — UI за ТЗ не оцінюється; верстка близька до Figma і адаптивна.
- **Сторінка з історією проходжень** — дані для неї вже є (усі проходження зберігаються), але UI в дизайні немає.
- **Відповіді в FAQ.** У макеті показана відповідь лише на перше питання, решту написано самостійно.
- **Фрейми IQ-тесту з секції Sign in у Figma** (Retake IQ Test, сертифікат тощо) — це залишки іншого продукту, тому реалізовано лише форму входу.

## Деплой

- **web** — Vercel: Root Directory `apps/web`, змінна `API_URL` = URL API.
- **api** — Render (free), див. `render.yaml`: міграції й сид виконуються при старті.
- **PostgreSQL** — Neon (free), рядок підключення передається в `DATABASE_URL`.

На безкоштовному плані Render API засинає після простою, тому перший запит може тривати 30–50 секунд.
